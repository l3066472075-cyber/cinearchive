# 影境档案 · CineArchive —— 影视教育资源库 设计蓝图

> 一份「会生长的好电影档案馆」的完整设计规格书。
> 定位：**影视教育 + 艺术治疗**。不是视频库，而是好电影的深度档案库。

---

## 0. 一句话定位

> 用户说「我现在很无力，和青春期孩子交流不顺」，系统从一座精选好电影的深度档案里，
> 挑出一部真正懂他的片子，讲清「为什么是它、它能怎么帮到你」；而用户的每一次搜索与反馈，
> 都会变成档案的新养分，让这座库越来越懂人心。

---

## 1. 关键边界：影视资源库 ≠ 视频资源库

| 维度 | 视频资源库（不是我们要做的） | 影视资源库（我们要做的） |
| --- | --- | --- |
| 核心资产 | 视频文件、流媒体、播放 | **元数据 + 深度解读 + 情感/治疗维度** |
| 存储 | 大体积视频、CDN、转码 | 结构化文本档案（SQLite 即可，可扩向量库） |
| 用户价值 | 「能看」 | 「能懂、能被接住、能获得支持」 |
| 版权 | 需播放授权 | 仅存资料性信息，不涉及视频分发 |
| 增长方式 | 上架更多片源 | **搜索/反馈驱动标签与解读迭代** |

因此，数据模型**不设计视频流字段**，而是把重心放在：`深度解读`、`支持人群`、`支持方式`、
`治疗说明`、`触发预警`、`讨论问题` 这些「让电影产生疗愈力」的字段上。

---

## 2. 核心创新：三维标签体系（影视教育 × 艺术治疗的桥梁）

这是整个系统区别于普通电影数据库的灵魂。我们把每一部电影，从「情绪/境遇/人群」三个
维度做了**可查询、可增长**的标注：

| 类别 category | 含义 | 示例 |
| --- | --- | --- |
| `emotion` 情感状态 | 观众此刻的内在感受 | 无力感、悲伤、焦虑、内疚、迷茫、孤独、羞耻 |
| `situation` 人生境遇 | 观众正身处的外部处境 | 亲子冲突、青春期、职业倦怠、丧失与哀伤、学业压力、面对疾病 |
| `audience` 支持人群 | 这部电影最能支持谁 | 青春期孩子父母、经历丧失者、职业倦怠者、照护者、低谷中的人 |
| `value` 价值资源 | 电影能给予的内在力量 | 希望、勇气、接纳、自我认同、韧性、和解、尊严、陪伴 |
| `theme` 影片主题 | 影片本身的主题（教育向） | 成长、亲情、师生情、友谊、死亡、梦想、教育、自由 |

**为什么这样设计**：用户描述的是「情绪 + 境遇」（我很无力 + 和青春期孩子交流不顺），
而电影被标注的也是「情绪 + 境遇 + 人群」。于是「人」与「片」可以在同一个语义空间里被
对齐、被匹配——这就是推荐能被「听懂」的基础。

每部影片还附有结构化的**深度解读**（`deep_analysis`）：

- `theme` 主题
- `art_value` 艺术价值（电影教育角度）
- `edu_value` 教育价值
- `therapy_value` 治疗价值

以及**安全使用层**：`support_audiences`（支持人群）、`support_types`（支持方式）、
`therapy_notes`（观影治疗使用说明）、`trigger_warnings`（触发预警）、
`discussion_questions`（观影后讨论问题）——这些是艺术治疗场景下「负责任地推荐」的关键。

## 3. 数据模型

> 采用 SQLite + SQLAlchemy 2.x（MVP 零配置）。JSON 列用于灵活内容，关联表用于可查询维度。

```
Movie 影片档案 (1)
 ├─ 元数据：title/title_en/year/director/cast[]/country/duration/genres[]/release_date
 ├─ 评分：rating_domestic(豆瓣) / rating_international(IMDb) + 各自的 source
 ├─ synopsis 简介
 ├─ deep_analysis{} 深度解读（theme/art_value/edu_value/therapy_value）
 ├─ support_audiences[] / support_types[] / therapy_notes
 ├─ trigger_warnings[] / discussion_questions[]
 └─ curated 是否人工精选

Tag 标签 (N)  <—— 可增长的维度轴
 ├─ name / category(emotion|situation|audience|value|theme)
 ├─ description / source(curated|user|ai)
 └─ use_count  ← 被搜索使用的热度（自增长的核心信号）

MovieTag 影片-标签 (N:N, 带权重)
 ├─ movie_id / tag_id / weight / source

SearchLog 搜索日志 (N)  ← 「搜索即喂养」的原料
 ├─ raw_query / normalized_query
 ├─ intent_labels[]（识别出的情感/境遇标签）
 ├─ matched_movie_ids[] / chosen_movie_id
 └─ source(recommend|search)

Feedback 反馈 (N)  ← 转化为标签/档案的增量贡献
 ├─ search_log_id / movie_id
 ├─ helpful / rating / comment / suggested_tag
 └─ status(new|applied|rejected)
```

关系要点：`Movie ↔ Tag` 多对多（带权重），`SearchLog`/`Feedback` 是让「使用」沉淀为
「资产」的两张关键表。

## 4. AI 推荐引擎

推荐是把「人话」翻译成「电影」的管线，**离线可跑、接大模型更强**：

```
query（"我现在很无力，和青春期孩子交流不顺"）
   │
   ▼ ① 意图识别 extract_intent
   ├─ 直接匹配库内标签名
   └─ 同义词词典映射（"交流不顺"→亲子冲突，"无力"→无力感 …）
        ⇒ intent = ["青春期","无力感","亲子冲突"]
   │
   ▼ ② 向量化（查询 = 原始自述 + 规范化意图标签）
   ├─ 配置了 embedding → 调 OpenAI 兼容接口（可接 bge/qwen/openai）
   └─ 否则 → 离线字符 n-gram 特征哈希（零依赖）
   │
   ▼ ③ 语义召回（对影片向量索引算余弦相似度）
   │
   ▼ ④ 标签加权 + 质量重排
   ├─ 意图标签命中数 / 意图总数（有意图时权重提升）
   ├─ audience 定向加成
   └─ 评分质量（豆瓣+IMDb 归一化）
   │
   ▼ ⑤ 生成解释 explain_recommendation
   ├─ 有 LLM → 大模型写 100~150 字温暖、不评判的推荐理由
   └─ 无 LLM → 模板化解释（离线）
   │
   ▼ 输出 Top-N + 契合度 + 命中标签 + 解释 + search_log_id
```

**推荐引擎的「负责」原则**：解释不夸大疗效、不说教、不贴标签；命中标签透明展示；
`trigger_warnings` 在详情页显著提示——这是艺术治疗产品的伦理底线。

## 5. API 接口设计（REST，自动生成 OpenAPI 文档）

Base：`/api/v1`，交互式文档 `/docs`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/recommend` | **核心**：输入情绪/境遇自述 → 电影推荐 + 理由（同时写入搜索日志） |
| `POST` | `/search` | 关键字/语义搜索（同样写入搜索日志） |
| `GET` | `/movies` | 影片列表（可按 `theme`/`audience`/`min_rating` 过滤） |
| `GET` | `/movies/{id}` | 影片完整档案（含深度解读、治疗维度、标签） |
| `POST` | `/feedback` | 提交反馈；`suggested_tag` 会自动入库并挂到影片 |
| `GET` | `/tags` | 标签列表（可按 category 过滤） |
| `GET` | `/themes` | 按分类组织标签（供前端筛选/导航） |
| `GET` | `/insights` | 库增长洞察（top 查询 / 未满足需求 / 待采纳标签） |
| `GET` | `/health` | 健康检查（含 llm/embedding 是否启用、影片/标签/搜索计数） |

**推荐请求示例**：

```json
POST /api/v1/recommend
{ "query": "我现在很无力，和青春期孩子交流不顺", "limit": 5 }
```

**推荐响应要点**：`intent_labels`（识别出的情绪/境遇）、`items[]`（每项含 `movie` 完整档案、
`score`、`matched_tags`、`explanation`）、`search_log_id`（用于后续反馈闭环）。

## 6. 「搜索即喂养」的自增长闭环

这是「每个人使用都会成为资源库助力、不断迭加升级」的机制设计：

```
用户搜索/推荐 ──► 写入 SearchLog（原始自述 + 意图标签 + 命中影片）
     │
     ├─ 意图标签 use_count +1          —— 高频情绪/境遇自然升温（词典自强化）
     │
用户反馈 ──► 写入 Feedback
     │
     ├─ suggested_tag 自动创建标签并挂到影片（weight +1）—— 标签体系由用户共同生长
     │
策划者/AI 看「库在生长」洞察
     ├─ top_queries     大家在找什么      —— 指导补充什么电影
     ├─ emerging_needs  未被满足的心事    —— 指导新增什么标签/解读
     └─ pending_tag_suggestions 待采纳标签 —— 用户贡献的新词汇
```

**三条增长飞轮**：

1. **词典飞轮**：每次搜索给意图标签「升温」，越多人找的「情绪」越容易被识别、被匹配。
2. **标签飞轮**：用户反馈建议的新标签（如「亲子沟通」）自动入库并挂到影片，索引立即
   失效重建，下一次搜索就能命中它。
3. **内容飞轮**：洞察页把「未被满足的心事」暴露给策划者（人或 AI），据此新增影片、
   补标签、写解读——库越用越懂人心。

## 7. 信息架构与页面路由

单页应用（SPA），锚点导航 + 弹层详情，路由语义清晰：

| 路由/区块 | 名称 | 内容 |
| --- | --- | --- |
| `#recommend` | 为我推荐 | Hero + 情绪输入框 + 意图标签 + 推荐卡片 |
| `#library` | 影片档案 | 筛选（人群/主题）+ 影片网格 |
| `#growth` | 库在生长 | 统计 + 大家在找什么 + 未被满足的心事 + 用户新标签 |
| （弹层） | 影片详情 | 深度解读四象限 + 治疗维度 + 讨论问题 + 触发预警 + 反馈 |
| `/docs` | API 文档 | Swagger UI |

**推荐卡片的信息层级**（从"懂你"出发）：影片标题 → 契合度 + 命中标签 → 推荐理由 →
快捷反馈（帮到我了/没帮到）。理由优先于元数据，因为用户要的是「被接住」，不是「查资料」。

## 8. 视觉设计语言（高级美感）

定位为「**电影档案馆**」式的沉浸体验，而非普通的数据库表格：

- **色彩**：暖调影院黑（`#100e0c` 深底）+ 香槟金点缀（`#c9a15c`）+ 暖奶油文字，克制而有温度。
- **字体**：衬线体（Cormorant Garamond / Noto Serif SC）做标题与品牌，传达「经典电影」气质；
  Noto Sans SC 做正文，保证可读性。
- **质感**：胶片颗粒噪点 + 环境光晕（aurora）+ 卡片悬停微光，营造「走进放映厅」的沉浸感。
- **海报占位**：无版权海报时，用标题首字 + 暖调渐变生成「艺术海报」，8 套色板按片名散列，
  既有辨识度又不失高级。
- **动效**：滚动渐入（IntersectionObserver）、卡片悬浮抬升、金色聚焦光、弹层缓入；支持
  `prefers-reduced-motion` 降级。
- **伦理表达**：触发预警用克制的红色提示，不制造焦虑；文案口吻温暖、不评判。

## 9. 技术栈与可扩展路径

**当前技术栈（前后端分离）**

- **后端**：Python 3.12 + FastAPI + Uvicorn（自动 OpenAPI）+ SQLite + SQLAlchemy 2.x
- **AI 层**：**LangGraph**（推荐流程状态图编排）+ **LangChain**（ChatOpenAI / OpenAIEmbeddings，
  OpenAI 兼容接口），离线 n-gram 哈希回退
- **鉴权**：PyJWT + 微信 `code2session`（静默登录），开发模式 mock
- **前端**：网页版为原生 HTML/CSS/JS（作 H5 预览）；小程序版规划为 Taro + React + TS

**生产化扩展路径（设计上已预留）**

1. **接真实向量库**：`ai/embeddings.py` 已把嵌入抽象成单一接口，换 PostgreSQL + pgvector
   或 Milvus/Qdrant 只需替换存储与检索两处。
2. **接大模型**：设置 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` 即启用个性化推荐理由；
   Embedding 同理（`EMBEDDING_BASE_URL` / `EMBEDDING_MODEL`）。
3. **用户维度（已实现）**：`SearchLog`/`Feedback` 已挂 `user_id`，可做个性化与人群分析。
4. **策划后台**：`/insights` 已是策划数据源，可扩一个「标签审核/影片录入」管理端。
5. **推荐可解释性**：`matched_tags` + `score` 已返回，可做归因与人工审核。

## 11. 架构演进（第二版）

在初版基础上，按「微信静默登录 + Taro 小程序 + FastAPI + LangChain/LangGraph」做了后端升级：

**A. LangGraph 推荐状态图**（`ai/graph.py`）

```
START → recognize_intent → retrieve → rerank → explain → END
         意图识别(词典)    语义召回   标签重排   理由生成(LLM/模板)
```

- `recognize_intent`：词典 + 同义词映射，纯函数（可被搜索复用）
- `retrieve`：LangChain 嵌入（离线哈希回退）做语义召回
- `rerank`：标签命中 + 质量 + 观众定向加权
- `explain`：LangChain ChatOpenAI 生成理由，模板回退

**B. 微信静默登录**（`auth.py` + `routers/auth.py`）

```
Taro.login() → code → POST /api/v1/auth/wx-login → code2session → openid
             → 建用户 → 签发 JWT → 后续请求携带 Bearer token
```

未配置 `WX_APPID/WX_APP_SECRET` 时自动进入开发模式（`wx_enabled=false`），用 code 派生
稳定伪 openid，保证本地联调零配置。

**C. 用户维度**：`SearchLog`/`Feedback` 新增 `user_id`，推荐/搜索/反馈接口支持可选鉴权，
让「搜索即喂养」从全局聚合升级为「可归因到每个用户」。

**D. 下一步（前端）**：Taro + React + TypeScript 微信小程序，四页面（推荐 / 片库 / 详情 /
库生长），`Taro.login()` 静默登录，复用现有 REST API。
